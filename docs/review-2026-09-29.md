2026-09-29, on `main` at `0592e1f` (the #8 release). Read-only: nothing in the
repository was changed. Every finding names a file and line. **seen** = reproduced
by running the app here; **read** = traced in the code by hand; **reported** =
raised by a review pass and not independently traced.

  That let the save flows run, which no CI suite does. The stand-in and the
  faked session are committed as `scripts/pw/studio-standin.mjs`, the seed

## 3. Bugs and risks found

Ranked by what it would cost the owner. **High** = data, the published map or
an installed app can go wrong; **medium** = the studio or the map misleads, or
will break as the data grows; **low** = cosmetic or latent.

### 3a. High

1. **A failed nightly publish reports success, and can close "The map needs a
   look".** *read* — `.github/workflows/publish-map.yml:79` and `:86` pipe the
   script through `tee`, and nothing declares `shell: bash`, so GitHub runs the
   step as `bash -e {0}` *without* `pipefail`: the step's status is `tee`'s. The
   comment at `:71-73` believes the opposite. A publish that fails (database
   unreachable, the shrink guard refusing) leaves `job.status = success`; the
   check then runs on the old file, finds "Nothing to report", and the last step
   **closes** the issue with "All clear". A data *problem* found by
   `check-map-data.mjs` (exit 1) likewise does not stop the commit that follows,
   contrary to README's "stops the publish". Fix: `defaults: run: shell: bash`
   at the top of the workflow — one line, `pipefail` on for every step.

2. **"Draw the return trip" can overwrite a direction that is already drawn.**
   *read* — the toast at `src/studio/StudioApp.tsx:468-485` appears after
   *every* save, including an Edit of a route whose both directions exist.
   Pressing it calls `draw.start(routeId)`; the save panel then has `parent`
   but `slotReversed === null` (`StudioApp.tsx:152-155`: no row with
   `shape === null`), so `reversed` falls back to the geometry guess
   (`SavePanel.tsx:177`), the same-ends check is skipped (`routeLocked`), and
   `routesWrite.ts:185-187` runs `update(drawn).eq('route_id', …).eq('reversed', …)`
   — which matches the existing drawn row and replaces its line. Fix: offer the
   button only while the route still has a slot, and add `.is('shape', null)` to
   that update so a drawn row is never a slot's target.

3. **A deleted direction cannot be drawn again by `+ New Route`, and the
   refusal says the opposite.** *read* — `routesWrite.ts:208-211` deletes the
   row, though its own comment (`:204-207`) says "Emptying a direction leaves its
   slot: a route always has two". The route is left with one row, so the card
   cannot flip (`otherDirection` is null) and no slot exists. Redrawing that
   direction with `+ New Route` and the same ends hits `route_ends_unique` →
   `claimExistingRoute` → `mine` is undefined (`:90`) → "A route between these
   two places already has this direction drawn" (`:92`). The only way out is to
   delete the whole route. Fix: empty the row into a slot (`shape: null`,
   `control_points: []`, `segments: []`, borrow fields cleared) and delete the
   route only when both are empty — what the comment promises.

4. **A route save will fail once there are a few hundred hintuans.** *seen* (the
   request) / *read* — `src/studio/stopsWrite.ts:178-183`. `syncHintuanLinks`
   deletes stale links with `.in('stop_id', drop)` where `drop` is **every
   hintuan the line does not pass**. Today that is ~20 ids in the URL; at the
   500 hotspots `studio-scale-test` plans for, it is a 19 kB request line, past
   what the gateway accepts. Observed on every save here:
   `DELETE /rest/v1/route_stop?route_variant_id=eq.…&stop_id=in.(…every id…)`.
   Also `:164-170` reads the hintuans with a bare `select('*')`, not `readAll`,
   so past 1,000 rows the sync silently sees a subset. Fix: read the direction's
   current links (one small request) and delete only the hintuan links no
   longer passed — usually none; page the hintuan read.

5. **The "map published for a newer version — Reload" button cannot do what it
   says under the installed app.** *read* — `src/commuter/CommuterApp.tsx:188`
   calls `window.location.reload()`, but with `skipWaiting: false` and
   `registerType: 'prompt'` (vite.config.ts) the old worker keeps control and
   serves the same old shell from its precache; the banner comes straight back.
   `pwa.ts:85 reloadToUpdate()` is the call that swaps the worker first. Fix:
   use it when a worker is waiting; otherwise `registration.update()` then
   reload.

### 3b. Medium

6. **The stop table is read twice on every studio load.** *seen* —
   `src/studio/live.ts:57` (`listVariants` reads the stops to name the
   directions) and `:111` (`loadStopsFromSupabase` reads them again); the
   stand-in logged two full `stop` reads per load, four under StrictMode. Fix:
   one read shared by both hooks.

7. **The count pill counts directions and calls them routes.** *seen* —
   `src/studio/StudioApp.tsx:410-411` shows `saved.variants.length` as "N
   routes": today's 5 routes read "10 routes", and saving one route (its drawn
   direction plus its empty slot) made it "12 routes". Fix: count distinct
   `route_id`s, or say "directions".

8. **Renaming a hotspot leaves every route name stale until the next route
   save.** *read* — names are generated at load (`live.ts:59 nameVariants`) and
   stored on the rows; `onSavedStop` (`StudioApp.tsx:257-262`) reloads the
   stops only. Cards, the list and the pill keep the old generated names. Fix:
   `saved.reload()` there too, or derive names from `stops.stops` at render.

9. **Keyboard shortcuts die after signing in from the Done dialog.** *read* —
   `signingIn` (`StudioApp.tsx:94`) is set true at Done (`:238`) and cleared only
   by the dialog's Dismiss (`:586`); a successful sign-in hides the dialog
   through `signedIn` and never clears it, so `keys={… && !signingIn …}` (`:514`)
   stays false: Ctrl+Z, Enter and F are dead for the rest of the session. Fix:
   clear `signingIn` when `signedIn` becomes true.

10. **The "Where am I" halo is drawn at half the fix's accuracy.** *read* —
    `src/commuter/Walker.tsx:14` uses the 256-px-tile constant `156543.03`;
    MapLibre's world is 512 px at zoom 0, which `directionArrows.ts:182`
    knows (`78271.52`, "half the 256 px figure"). `where-test.mjs:102,109`
    asserts the wrong constant, so the suite passes. Fix: one shared
    `metresPerPixel`; update the test with it.

11. **After a GPS timeout, "Where am I" cannot be turned off.** *read* —
    `useWhereAmI.ts:167` sets `status = 'error'` but leaves the watch
    registered; the button then reads off (`WhereAmI.tsx:24`), and its tap runs
    `ask()`, which returns at `:127` because `watchRef` is set. Fix: decide
    stop/ask on `watchRef`, and keep the failure as a note beside `'asking'`.

12. **Undo down to zero points leaves the old draft in storage.** *read* —
    `useDrawing.ts:567-584` writes the draft only with points and removes it
    only when not drawing; drawing with no points does neither, so a reload
    restores what was undone (extend-test notes it). Fix: `removeItem` in that
    case.

13. **A save whose link sync fails cannot be retried.** *read* —
    `SavePanel.tsx:236-258`: `saveVariant` succeeds, `syncHintuanLinks` throws,
    the panel shows the error with the same inputs; the second Save inserts the
    route again → unique violation → `claimExistingRoute` → "already has this
    direction drawn". PLAN.md's known risk #3 (saves are not transactional)
    covers the shape; this is the concrete dead end. Fix: after the row is
    saved, keep its id so a retry is an update — or call `onSaved` with a
    "links not synced" notice.

14. **Unit tests assert on the committed map, and the publish that changes it
    starts no CI run.** *reported; consistent with `ci.yml:24-26`* — six unit
    files require ≥2 lines, ≥10 boxes, a cut > 0 and so on from
    `public/data/map.json`; a nightly commit with `GITHUB_TOKEN` triggers no
    workflow, so `npm run check` on `main` can go red unnoticed. Fix: run
    `npm run test:unit` in `publish-map.yml` after the check, or make those
    assertions SKIP as the suites do.

15. **Deleting a terminal that is a route's end shows a raw Postgres message.**
    *read* — `stopsWrite.ts:153-156` deletes; migration 0006 makes
    `head_stop_id`/`tail_stop_id` plain foreign keys with no `ON DELETE`, so
    the database refuses (correctly) and the notice is its error text. Fix:
    refuse in `onDeleteStop` naming the routes that end there.

16. **`deleteVariant`'s clean-up never reads its errors.** *read* —
    `routesWrite.ts:213-220`: the count query's error is ignored (a failed count
    leaves `count` null, so `count === 0` is false) and the two deletes' results
    are dropped; a refused clean-up leaves an orphan route silently.

17. **`check-map-data.mjs` ignores its file argument unless `--markdown` is
    also given.** *seen* (`node -e`) — `scripts/check-map-data.mjs:179`: with
    `mdAt = -1`, `i !== mdAt + 1` drops index 0. CI always passes `--markdown`,
    so it hides. Fix: `!(mdAt >= 0 && i === mdAt + 1)`.

## 4. The studio, specifically

What was exercised offline and held up: opening with 10 directions and 72
hotspot features; tapping a line (the route list, one way round, in the card
colours); Escape; `+ New Route`, three clicks with a router that has no road
(both segments fall back to freehand, "3 points · 762 m · 2 freehand"), Ctrl+Z,
Done without a session (the sign-in door), reload (the draft comes back); with a
session: Done → the save panel; Save with the same place at both ends ("The two
ends have to be different places."); Save with two ends (route + two directions
written, the "Saved · Draw the return trip" card, the draft cleared);
`+ New hotspot` → Hintuan, four corners, Done → the hotspot panel listing the
directions the outline passes, Save (stop written, links replaced); the new
hintuan's card, Edit hintuan (the tracer re-opens with its four corners).

**What the CI suites never reach**, because they run without an account: the
save panel and every path in `routesWrite.ts` (the unique-violation claim, the
slot fill, the route-row clean-up), `stopsWrite.ts` (`replaceLinks`,
`syncHintuanLinks`), `deleteVariant`, Edit route on a saved direction, "Draw the
return trip", Delete and its confirms, the password flows, Enter → Done and F →
freehand, the freehand toggle for new clicks, a draft restore of an edit,
router failure paths (timeout, 429), a basemap switch mid-drawing. Findings 2,
3, 4, 6–9, 12, 13, 15, 16 all live there. The stand-in used for this review
(`scripts/pw/studio-standin.mjs`: a `page.route` on `/rest/v1/` that answers
reads from `map.json` and echoes writes back, and a faked stored session)
would let one more suite cover the save flows on every push, without an
account and without touching the live tables.

## 5. Proposed folder structure

Principles: keep the four areas and the guard that checks them (it reads the
first path segment, so folders inside an area need no change to it); one level
of folders inside `shared/` and `studio/`, none inside `commuter/`; a file used
by one side moves to that side when the reason is structural, not a redesign
decision; tests leave the tooling folder; no module is renamed, only moved, so
every change is an import path or a doc line. Behaviour is unchanged and the
existing suites prove it after every step.

Decisions inside that, and why:

- **`supabase.ts` into `studio/data/`.** All ten importers are studio files; the
  public map must never import it, and today only the string net at the end of
  `vite build` would say so (as a chunk, not a file:line). In `studio/`,
  `check-boundaries.mjs` refuses the import at the source.
- **`mapFile.ts` into `commuter/`.** The published-file reader is the public
  map's by design (ADR 0001). `check-map-data.mjs` and `map-file-test.mjs`
  import it from `src/`, which scripts may.
- **`RouteSheet`, `RouteTripDetail`, `StopTimeline`, `Departures`,
  `babaanSides`, `liveryLine` stay in `shared/`** although one side uses each
  today: they are the card family the visitor redesign is being built from,
  and the studio's ride-to preview is drawn with the same pieces. Moving them is
  a decision about the redesign, not about tidiness. (The UI pass notes the
  family has two generations — the redesigned, token-clean `RouteDock/Card/…`
  and the older `Sheet/HotspotCard/RouteSheet/StopTimeline` — which the
  redesign will settle.)
- **`useSavedRoutes`/`useSavedStops` go under `map/`, not `model/`:** they own
  MapLibre sources and layers; the model files own no React.
- **Stories stay beside their component**, as now.
- **`.walker*` CSS moves out of the shared stylesheet** into a file imported by
  `Walker.tsx` (`.ride-dot` likewise, beside `rideTo.ts`), so a page's own
  styling stops being global CSS the other page also loads.
- **`tests/` beside `scripts/`.** The unit files and the suites are tests; the
  guards and the publish are tools. One
  `node --test 'tests/unit/*-test.mjs'` with the TypeScript hook replaces eleven
  chained npm scripts, runs the files in parallel and reports per file.
  `scripts/pw/` becomes `tests/e2e/`.
- **Left alone on purpose:** `PLAN.md` (the owner's journal; its historical
  paths stay true as history), `CONTEXT.md`, `docs/`, the migrations, the font
  sources (their README explains them; Vite ships only the six wired `.woff2`).

What has to change with the moves (every reference found by grep, none in
`node_modules`): `package.json` (script paths; the 11 `test:*` entries collapse
to one), `.github/workflows/ci.yml` (ten `scripts/pw/` lines and the `test:unit`
comment), `publish-map.yml` (`:79`, `:86`), `README.md` ("Where things are" and
four command lines), `scripts/pw/README.md` (moves with the suites),
`.claude/agents/ds-reviewer.md` (`:20,66-68,96,104`),
`.claude/skills/ds-component/SKILL.md:57`, `.claude/skills/sync-tokens/SKILL.md:62`
(`npm run test:map-colours` → a name pattern), `.claude/agents/ux-researcher.md:51`,
`vite.config.ts` (four comments), `public/.assetsignore:2`, and the `../src/`,
`../public/` relative paths inside the moved scripts and tests. In `src/`,
roughly 180 import lines are a mechanical rewrite that `tsc --noEmit` and the
boundary guard check in full.

## 8. Lighter for visitors, scalable in the data — what the numbers say

Added after the owner's ask of 2026-09-29: "make the app lighter for users to
use and scalable in the future". Everything below was measured here on the
production build and the repository's own scale suites.

### What a first visit to `/` downloads today (gzipped, from the build)

| bytes | what |
| --- | --- |
| 338 kB | the shared chunk: MapLibre (most of it), React, the shared code |
| 135 kB | MapLibre's tile worker |
| 290 kB | six font files (woff2; gzip does nothing to them) |
| 19 kB | CSS |
| 17 kB | `map.json` (99 kB raw) |
| 8 kB | the public map's own code |
| 3 kB | `index.html`, the manifest, workbox, the worker |

About **810 kB before a single basemap tile**. Then OpenFreeMap: the style,
the sprite, the glyph ranges (three faces), and tiles — a central-Manila tile
at zoom 14 is ~450 kB (README), the opening view at zoom ~11 loads a handful
of smaller ones. So: the basemap is the largest download and the one least
ours; the fonts are the largest that is entirely ours; our own code is 1%.

A repeat visit is already light: the worker precaches the shell (JS, CSS,
icons, the figure), so only `map.json` (NetworkFirst, 3 s) and unseen tiles
cross the network. The fonts are **not** precached (the glob is
`assets/*.{js,css}`), so offline the text falls back to system fonts once the
HTTP cache lets go.

### Lighter, now — each measured

1. **Fonts: 283 → 142 kB by subsetting to Latin.** Each SN Pro cut carries
   1,196 glyphs; the app needs about 620 (Latin, punctuation, ₱, arrows).
   Five weights → three (Regular, Bold, Black — Medium and SemiBold each sit
   one step from a neighbour) → about 90 kB. Precache what remains (+90 kB
   stored; offline text right). Roughly −190 kB per first visit, a quarter of
   the app's own payload, one PR.
2. **Basemap: bound the map to Metro Manila** (`maxBounds`) so a stray pan
   never fetches the world; keep the opening zoom; and measure the two styles
   on a real network before choosing the default (the numbers above stop at
   the app's own bytes — the tile cost needs DevTools on a phone).
3. **Our chunk: name it, do not fight it.** 8 kB of app code; MapLibre is the
   weight, and its worker/GPU model is what keeps 2,500 lines smooth. A
   smaller map library would cost more than it saves.
4. **Main thread: nothing to do at today's size** (idle within a second). The
   work is in what comes next.

### Scalable — where the app breaks as the data grows, with today's numbers

The published file costs 6.8 kB per direction raw (21 points per km,
6-decimal coordinates) and compresses 5.9:1. Metro Manila has on the order
of 700–900 jeepney routes, so 1,500–2,000 directions is the realistic
ceiling for this map alone.

| directions | `map.json` raw | over the wire |
| --- | --- | --- |
| 10 (today) | 99 kB | 17 kB |
| 1,000 | ~7 MB | ~1.2 MB |
| 2,500 (the scale suite, run here) | 23 MB | ~4 MB |

The repository's own `scale-test` here, at 2,500 directions and 507 hotspots,
no tiles, on a desktop-class CPU: map load 5.0 s, **first line on the screen
8.7 s**, 4.2 s in long tasks, idle at 10.5 s. Where the time goes is MapLibre
building the sources from the whole file, not our code (the top own-code
entry is `near` in `stops.ts` at 63 ms). A phone is three to five times
slower: half a minute to the first line, after a 4 MB download. The budgets
the suite enforces (30 s, 20 s) accept that; "light" does not.

The cause is the shape, not the code: one file, every line in full, parsed
and painted whole before anything shows. Three shapes, in order of reach:

**A. Index + overview + lines on demand** — no new infrastructure; the
publish script writes three things instead of one.
- `map/index.json`: every route, its ends and names, every hotspot's point and
  box, the links, and an *overview* line per direction simplified at 5 m with
  5-decimal coordinates — **1.5 kB per direction instead of 5.7** (measured on
  today's lines: 27% of the points; invisible at zoom ≤ 14, where a pixel is
  ≥ 7 m). At 1,000 directions ≈ 1.5 MB raw, ~250 kB over the wire; the whole
  map, every card, the list and a search draw from it.
- `map/lines/<direction>.json`: the full line (6 kB raw, ~1.2 kB gz), fetched
  when a direction is lit or opened — which is when the orange stretches, the
  chevrons, the ride-cut and the babaan sides need it. The worker's runtime
  cache keeps every line seen, so offline keeps what was ridden.
- The orange stretches are computed today on the client for every direction
  × hotspot at load (1,580 of them at 2,500 directions); the publish can
  write them into the index (it already runs the same rule in
  `check-map-data`), and the client computes only for the line it lit.
At 1,000 directions: ~300 kB to the first paint instead of 1.2 MB, one
overview source instead of a thousand full lines — under a second on a phone.

**B. Vector tiles for the overview** (PMTiles: one static file on Cloudflare
with range requests, no server; MapLibre fetches only the tiles in view, at
that zoom's simplification; `promoteId` keeps the feature-state lighting).
The publish would run tippecanoe; the client adds the pmtiles protocol
(~30 kB). Everything else in A stays. Needed when the index itself gets heavy
— beyond ~3,000 directions, or hotspots in the thousands, or a
Philippines-wide map.

**C. Stay with one file and simplify it** — about 2× cheaper, still whole-file;
not worth a step of its own.

Recommendation: **A, after the restructure** — it lands in `shared/model`,
`mapFile.ts` and the publish script, and the file's schema version makes the
switch safe (the "newer map" banner already handles an old app meeting a new
file, once finding 5 is fixed). Build A so that B slots in later: the
index/detail split is exactly what B needs too.

### The studio at scale

`studio-scale-test` here, at the same 2,500 directions and 507 hotspots
against a stand-in for the database: **first line at 20.5 s**, 7.9 s in long
tasks, 66 requests, **141.7 MB received** — of which the direction list is
133.6 MB (the stop table is read 4× and the links' 28 pages 2×: development
renders twice, so halve these for production, and note the double stop read
is finding 6 at scale). The list already leaves `control_points` and
`segments` out (2026-09-25) and asks for its pages together, but it still
carries `shape` — the full line, a point every 20 m — for every direction:
**~27 kB per direction** as the stand-in serves rows with the 15-decimal
coordinates older saves kept, ~15 kB with the 6 decimals a save keeps now.
At 1,000 directions that is 15–27 MB every time the studio opens.

The remedy is the same shape as A, and the studio already has half of it:
`withDrawing` reads one direction's drawing on demand. What is missing is an
`overview` column — the line simplified at 5 m, ~1.5 kB — written by the save
beside `shape` (the lines are JSONB GeoJSON, no PostGIS, so the client
simplifies; a one-off script backfills the rows that exist) and selected by
the list instead of `shape`. The studio opens on ~1.5 MB at 1,000 directions;
the full line is read when a direction is opened, followed or lit, as the
drawing already is. The publish then reads `overview` for the index and
`shape` for the per-direction files, so A and this are one change to the
data, not two.

After that, the cliffs in section 3: the link sync's URL and unpaged hintuan
read (4), the second stop read (6), and `stopsAlong` in render plus
`labelGroups` O(n²) (6.9). Beyond those, nothing structural until several
thousand rows.

### The database and the publish

Visitors never touch the database (ADR 0001): the only egress is the nightly
publish and the owner's editing, so Supabase's free tier is not a ceiling for
readers. The publish reads whole tables in pages; at 2,000 directions that is
~15 MB once a night — fine. `route_stop.stop_sequence` as a vertex index
(known risk #2) is the one schema item that gets harder with more routes to
re-snap; the metres-along-the-line key was already decided (M8).

### Folded into the order of work (section 7)

The fonts (lighter) are one PR and can ride with step 1 or 3. Shape A
(scalable) comes after step 2 (the moves) and step 4 (the studio fixes), as
its own step, with the scale suite's budgets tightened to what A achieves —
first line within 5 s at 1,000 directions on a runner — so it cannot regress.
